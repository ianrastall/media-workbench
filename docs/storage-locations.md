# Next milestone: choose where Media Workbench works

Recorded 18 October 2026. **In progress; not complete or released as 0.4.0-alpha.1.** Drive containment is the next release milestone, ahead of queue/warm-worker work and further model expansion. The intended release is **0.4.0-alpha.1**, subject to the acceptance checks below; do not label a release as that milestone until it works. Intermediate alpha releases may ship completed, headless-verified slices.

**Slice 1 implemented (unreleased, after 0.3.0-alpha.1):** app-owned temporary work now lives in the saved data folder's `temp/` folder. Each Python worker gets `temp/work/<id>` as its `TEMP`/`TMP`/`TMPDIR`; setup and GPU children get their own folder there, and NVIDIA's compiled-kernel cache (`CUDA_CACHE_PATH`) and `TORCH_HOME` move under `cache/`. Painted-area hand-overs (Create and MCP) use `temp/painted`, and update installers download to `temp/updates` after a free-space check. A data folder that is missing, unwritable, or reached through a junction stops the operation with a plain explanation; nothing falls back to Windows temp. Read-only operations (health, hardware profile, Hub search/details, model inspection) still never create a missing data folder. Crashed workers' folders are removed by Rust clean-up unless a live worker holds them open, and the old `%TEMP%` locations are only swept. Headless checks only; no process-write trace or GPU run has been made with these changes.

## Problem and current evidence

Choosing a data folder does not currently choose every write location. An SSD can be unsuitable because it is small, nearly full, reserved for Windows, or simply excluded by the user. Installing the app on another drive does not redirect Windows' temporary directory or profile defaults.

Source inspection at `e493113` found:

| Area | Current behavior and source |
| --- | --- |
| Default data folder | Local AppData until a saved folder overrides it (`MainViewModel.cs`). |
| Models, private inference runtime, outputs, jobs and normal worker logs | Under the saved data folder. Setup explicitly places uv's cache there, and inference explicitly sets `HF_HOME` there (`inference_setup.py`). |
| Worker temporary files | The C# supervisor and Python setup/inference children inherit Windows temp settings (`PythonWorkerClient.cs`, `inference_setup.py`). This is an escape route; inspection alone does not establish which dependencies wrote there or how many bytes. |
| Painted-area hand-overs | Windows temp, including the MCP path (`Housekeeping.cs`, `McpServer.cs`). |
| Update installer downloads | Windows temp (`Housekeeping.UpdateFolder`, `UpdateService.cs`). |
| Preferences and startup error logs | Local AppData (`MainWindow.xaml.cs`, `SettingsStore.cs`, `App.xaml.cs`). Startup logs rotate at about 1 MiB; this is distinct from large inference storage. |
| Application installation | Defaults to Local AppData's Programs folder (`packaging/media-workbench.iss`). Installer extraction/staging must also be audited. |

These are confirmed code paths, not a trace of the user's disk activity. No files were moved or removed during this audit, and no runtime containment or migration has been verified.

## Intended experience

1. Before any large download or job, choose **Where Media Workbench works**. Show available drives, free space, drive type, and the space the operation needs. Explain that this location holds models, pictures/videos, and temporary work. Remember an existing saved choice. Do not rank an SSD ahead of the user's exclusions or available capacity, hard-code drive letters, or silently choose another volume.
2. Use that work folder for every app-controlled large write: downloads, extraction, package/model caches, dependency scratch files, image hand-overs, video frames, update staging, and normal logs as well as models and results. Temporary work defaults to a managed subfolder there; a different temporary-work location is an Advanced option requiring an explicit choice and its own space check.
3. If the location is full, disconnected, unavailable or unwritable, stop before heavy work with a plain explanation and choices to free space, reconnect it, or choose another location. Never fall back to Windows temp, the user profile, or a different drive without the user choosing it. A restart, worker retry, repair, MCP operation, or app update must obey the same rule.
4. Settings should show the actual application, work, temporary, cache and preferences locations, their volumes, and what is retained. Advanced options should support an explicit restriction on which volumes may receive managed work; reading a user-chosen source and saving an explicitly chosen export are separate intentional actions. Do not force a beginner to configure environment variables.
5. Support keeping the application on the chosen drive as well: retain the installation destination on upgrade and expose the destination clearly during installation. Decide and document the bounded profile footprint (preferences/location pointer and startup diagnostics). Provide a supported way to keep app-owned settings and logs with the chosen location for users who want all app-owned files there; do not advertise this as working until launch, update and uninstall have been tested with it.

The promise covers Media Workbench and its owned processes. Windows may independently write paging, driver caches, crash reports, installer bookkeeping or security/antivirus data on the system drive. Measure and describe these separately rather than promising that Windows will never write there. Avoid changing global Windows temp, cache or paging settings.

## Implementation boundaries

- Centralize the saved storage policy and resolved locations for GUI, CLI/MCP, updater, supervisor and Python children. Rust should own managed path/volume validation and space policy behind the versioned C ABI; C# coordinates presentation/processes and Python remains out of process. Reject paths/links that escape the permitted managed locations; preserve the existing reparse-point protections. Check actual volumes, including mounted folders, rather than trusting a drive-letter prefix.
- Set process-scoped temporary and supported dependency cache locations before launching owned processes or importing dependencies. Audit `TEMP`, `TMP`, Python temporary-directory caching, uv/package extraction, Hugging Face, PyTorch/CUDA-related caches and SQLite temporary storage. Respect isolated Python behavior; environment changes alone are not evidence that each dependency obeys them. Carry the policy to every child and test actual writes.
- Check writable destinations and worst-case peak space on every volume receiving bytes, including compressed archives plus extracted files, updates and temporary frames. Aggregate simultaneous needs when locations share a volume. Keep a reserve and check during long writes; handle races, cancellation and disappearing drives without a second-location fallback. Drive speed can inform advice, but capacity and the user's choice take precedence.
- Keep bounded clean-up under the existing ownership/locking rules. Clean managed scratch after success/cancel/crash, retain retry downloads only under the documented policy, and protect images, videos, job records and private inputs required by Retry or **Use settings**. Legacy temp/profile cleanup must identify this app's own files precisely; do not sweep other applications' caches.
- Add an explicit **Move existing data** workflow. Today changing Settings only changes the path. Preflight destination space, block conflicting operations, copy and verify, repair recorded paths/index references, and switch settings atomically only after success. Keep the source intact until the verified switch and make source removal explicit. Interrupted moves must recover without data loss or silent redownloads. File/runtime/inference verification gates still apply; do not carry readiness forward unless its evidence remains valid for the resulting configuration.

## Release acceptance

- Headless checks exercise all location consumers, fake low-space/unwritable/missing volumes, shared-volume peak-space accounting, child environment propagation, containment/reparse refusal, and no automatic fallback. Include fresh/default setup, existing saved settings, CLI/MCP, discovery/download, repair, updates, and settings round trips. Do not test only the helper that constructs the paths.
- Migration checks cover cancellation/crash at each stage, conflicting workers, insufficient space, preserved original data, unchanged picture/video checksums, job/input/settings reuse, index rebuild, and honest readiness after the move.
- On a two-volume Windows test machine, explicitly select the larger non-system volume and exclude the system volume for managed work. Trace process-tree file writes during real setup (including package extraction), base/SDXL/video verification and generation, upscaling, painted changes through GUI and MCP, update download/install/relaunch, cancellation and crash recovery. Record actual outside-volume writes and peak space. Headless environment assertions are not proof of dependency behavior.
- Exercise disconnected/low-space work drives without filling the user's real system drive. Check fresh installation plus upgrade/uninstall on Windows 10/11, both the normal preferences arrangement and the supported all-app-owned-files arrangement. Installation/update temp handling is part of the gate, not a deferred exception.
- Run `./scripts/check.ps1`, `./scripts/build.ps1`, and published headless checks. Interactive and GPU checks require the user's availability; do not launch them during the pause. Record results in `docs/validation.md` and update README, current status and handoff before the version/changelog push triggers the Actions release.

## Acceptance decisions and tooling (18 October 2026)

The user decided the scope of 0.4.0-alpha.1's acceptance:

- **All-app-owned-files arrangement:** not part of 0.4.0-alpha.1. The milestone documents the measured footprint outside the data folder (preferences, startup log, the installation and installer bookkeeping) instead; the arrangement comes in a later release with its own launch, update and uninstall tests.
- **Clean-machine installs:** deferred and recorded as an open gap before 1.0. Windows Sandbox could not be enabled on the development machine (Windows reports a corrupted component store and the repair stalls); Windows 10 needs a VM or spare PC in any case.
- **Write trace:** Sysinternals Process Monitor, run on the development machine. C: is a 256 GB system SSD with about 23 GB free; D: is an internal hard disk that holds the data folder.

**Tooling (implemented; headless parts checked, the elevated capture not yet run):** `scripts/containment/trace.ps1` runs the acceptance. It creates `artifacts/containment-trace/<time>/` on the repository's drive, starts `trace-controller.ps1` elevated (one UAC prompt), and runs `acceptance.py`. The driver runs every phase through a fresh `MediaWorkbench.Cli.exe mcp` from the installed release, so the shipped C# supervisor sets each worker's folders as the app does. The phases are SD 1.5 setup, text/image-to-image/painted/4× upscale pictures, SDXL setup and pictures, video setup and a clip, Discover, cancel, killing the host mid-picture and recovering, Install / verify again, and the update download. Before and after each phase the controller starts, stops and exports a Process Monitor capture; it first checks which filter file (`procmon_config.py`) Process Monitor obeys and falls back to an unfiltered capture. `summarize_writes.py` rebuilds the app's process tree from each capture and writes `report.md`, listing changes by area: data-folder subfolders, the app folder, and anywhere else with profile folders shown as environment variables. The report also gives the lowest free space per drive and the largest `temp/`. `tests/test_containment_trace.py` checks the filter-file layout, change classification and tree attribution. `trace.ps1 -Quick -NoTrace` (read-only phases, no elevation) passed against the installed 0.3.0-alpha.9. Process Monitor is downloaded into the ignored `.tools/procmon/` and never committed.

**Short traced run, 18 October 2026 (installed 0.3.0-alpha.9):** `trace.ps1 -Quick` with the user accepting the UAC prompt. Process Monitor obeyed the filter file with UTF-16-terminated values on the first try: the calibration write was kept, with no read or registry events. The `inspect`, `discover` and `storage` phases changed files only inside the data folder (its `.operation.lock`, `temp/` and `temp/work/<id>` with its owner file, all removed again), and nothing elsewhere. Each phase's capture held the host's Process Create event, so the tree was attributed. That run also caught a missed read-only operation name (`QueryStatInformation`, now excluded).

**Full traced run, 18 October 2026 (installed 0.3.0-alpha.9):** all 12 phases passed. The only app writes outside the data folder were Python bytecode caches in the app folder on C:, now prevented with `-B` and removed by the installer on upgrade and uninstall, plus the NVIDIA driver's 0-byte open of its profile file. Details are in [validation](validation.md#drive-containment-write-trace-installed-030-alpha9-18-october-2026). The summarizer now lists NTFS records and paging writes separately as Windows bookkeeping.

**Repeat traced run on the installed 0.3.0-alpha.11 (18 October 2026):** clean. Apart from the NVIDIA driver's 0-byte profile open, the app changed nothing outside the data folder, and cancel records *cancelled*. See [validation](validation.md#repeat-drive-containment-trace-installed-030-alpha11-18-october-2026).

Still to do for the milestone, in order: low-space and disconnected-drive checks on a small attached virtual disk (a second UAC prompt); the interactive session with the user (GUI painted change, Cancel, crash recovery, an older alpha → 0.3.0-alpha.11 Update now and relaunch, never-use drive); then validation notes and the release.

## Resume here

Slice 1 (worker/update/painted paths) is done; see the table at the top. Slices 2 (locations in Settings), 3 (Move existing data) and 4 (drive choice before setup) are done. **Removing the old copy (0.3.0-alpha.4):** after a move, Settings offers **Remove the old copy…** (with a confirmation flyout; remembered across restarts as `MovedFrom`). Rust `mw_remove_moved_data` holds the old folder's lock and deletes only files whose copy in the current data folder has the same size and modification time, plus the old folder's own `temp/`, `library/` and `.removing/`, then empty folders, the lock file and the folder itself if empty. Files that differ or were added later are kept and counted. Saving a different folder forgets the old copy. **Never-use drives (0.3.0-alpha.4):** each drive in Settings has **Never use this drive** / **Allow this drive** (saved as `ExcludedDrives`, by drive root; a mounted folder counts as the drive whose letter it is under). Saving or moving the data folder onto an excluded drive is refused with a plain message, the question before setup never suggests one, **Use this drive** is hidden for it, and Settings warns when the current data folder is on an excluded drive. **Keep this drive** before setup allows that drive again. **Slice 4 implemented (0.3.0-alpha.4):** Settings lists **Drives on this computer** (ready fixed, removable and network drives, with quota-aware free space and type from Rust, and which one holds Windows); **Use this drive** fills in `<drive>\Media Workbench` without saving or moving. Before the first Install / verify, when the data folder is still the default on a drive with less free space than another non-network drive and was never chosen, Create asks where to work and setup waits until the user keeps the drive or saves another folder. The choice is remembered (`DataRootChosen` in preferences); folders saved by earlier versions count as chosen, and a ready installation is never asked. Installer: Inno Setup already reuses the previous install folder on upgrade (`UsePreviousAppDir` default) and shows the destination page only on first install (`DisableDirPage=auto`); its own unpacking uses Windows temp briefly. No installer change was made in this slice. **Slice 3 implemented (0.3.0-alpha.3):** Settings → **Move my data there…** checks the typed folder with Rust `mw_plan_data_move` (files and bytes to copy, free space with a 1 GiB reserve, same-volume note, and plain blockers: inside/containing the data folder, not empty, a link inside the data folder, not enough space), then **Move now** runs `mw_move_data_folder`: under the data-folder lock it copies everything except `.operation.lock`, `temp/`, `library/` (rebuilt) and `.removing/` into a marked `.<name>.moving` staging folder, hashes each file while reading, re-reads and compares the copy, keeps modification times (readiness stamps compare size and time), re-checks free space before every file, and renames the staging folder into place last. Only then are settings switched. The old folder is never changed; the app says it can be deleted in File Explorer once the new one is checked. Failure or cancellation removes the staging folder; a crash is recovered at the next start from `PendingMove` in preferences. Readiness carries over because the bytes and times are identical and the runtime, job and readiness records hold no absolute paths (checked on the development data folder); no GPU run after a real move has been made yet. Next, in order: (4) installer destination retention and the all-app-owned-files arrangement; (5) real write-trace acceptance on a two-volume machine with the user available. Location/volume validation is still C# (`WorkFolders.Prepare`) and Python (`owned`); moving it behind the Rust ABI belongs with the migration slice, which needs the same checks. Use ignored build/check output on a suitable development volume; development tools' own caches are a separate audit from the shipped application.
