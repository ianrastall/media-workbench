# Development direction after 0.3.0-alpha.11

The preference/startup-log migration is implemented, including an authoritative small location pointer, previous-settings recovery copy, commit-last pointer switches, retryable legacy cleanup, no fallback diagnostics, and restoring preferences when an existing working folder is chosen again. The original alpha.11 incident remains unreproduced; the silent-default class has been removed rather than claimed reproduced.

**Before the next storage release:** investigate the additional stale legacy preferences observed after the real alpha.13 migration ([evidence](validation.md#preferences-in-the-working-folder-030-alpha13)). The pointer and working preferences stayed correct, and the extra file was safely archived/removed manually. Its different hash and older timestamp have not been explained. Trace/reproduce it and consider verifying deletion before clearing the migration marker; do not count the manual cleanup as automatic-path acceptance.

Next complete slice: offer first installation in `<working folder>/App` and preserve it across updates. Plan first-start discovery of the folder from that arrangement so a colocated installation can avoid a profile pointer. Keep existing installations at their current path unless the user deliberately moves them, preserving taskbar targets and application identity. Verify new install, upgrade, data move, unavailable drive and uninstall; the uninstaller must preserve preferences, models, pictures and records. Installer extraction and Windows bookkeeping need explicit acceptance decisions. Then run the complete containment trace before naming the milestone 0.4.0-alpha.1.

After that, implement the curated Models Get coordinator described below. Reuse the existing prerequisite/download/GPU checks, keep total download/space costs visible, and retain technical setup controls under Advanced. This resume point supersedes the historical directions below.

## Working-folder startup gate (0.3.0-alpha.12)

The first implementation slice removes the silent default: first start requires a saved working folder, load failures stop work, saved missing folders are retained for recovery without recreation, and the chosen folder is checked before a worker starts. Browse, drive suggestions and existing-folder upgrades are implemented. The old alpha.11 incident's exact cause remains unknown; do not claim it was reproduced.

Next bounded slice: move preferences and startup diagnostics under the working folder, keeping only a small location pointer in Local AppData. Design crash-safe migration and recovery first: missing/invalid pointers, disconnected drives, old settings, a data-folder move and settings-save failure must preserve the last usable state and never authorize a fallback. Then support installation under `<working folder>/App` with upgrade/uninstall acceptance and the full containment trace. Only call the milestone 0.4.0-alpha.1 when its acceptance gates pass.

After the folder foundation: a Models view with curated choices and one Get action that chains prerequisite runtime/model setup, download verification and real GPU verification. Keep technical details and file imports under Advanced. Existing verification gates remain mandatory. No new video work or rename is part of these slices. This resume point supersedes historical directions below.

The initial curated list can use the existing SD 1.5 and SDXL recipes. Today `MainViewModel.InstallAsync` and `InstallXlAsync` expose separate steps, and `workers/python/addon.py` requires the verified base installation for SDXL's shared runtime and safety checker. The Get coordinator should check what is already ready, preflight space for all missing prerequisites, run base setup only when required, then run the selected model's setup and its real GPU check under one cancellable progress flow. Report the combined download rather than hiding its size; use measured timings where available instead of inventing a speed estimate. A failed or cancelled stage must leave that model unready, preserve safe retry data, and never select it in Create.

This is a plan, not a list of supported features. The implemented path is SD 1.5 text/image-to-image and painted partial changes, optional Stable Diffusion XL pictures, short SD 1.5 videos with AnimateDiff, adding SD 1.5-family models and single-file SDXL fine-tunes the user already downloaded or picks in Discover, a kept-loaded picture model and several versions per Generate, Real-ESRGAN upscaling, durable job evidence, indexed Library browsing and PNG export, storage maintenance with automatic clean-up and free-space checks, runtime settings chosen from the computer's hardware, and checksum-verified app updates. Those operations share one saved data folder and preserve model/runtime verification gates.

## Direction after the 0.3.0-alpha.11 checkpoint (18 October 2026)

**What the user found using the app as a beginner.** After setting up Stable Diffusion 1.5 and XL from the installed alpha.11, the user made a complete picture (not a good one) and found the app too complex to follow. The clearest example: the "Add a model you already downloaded" card ("one .safetensors file, or a Diffusers model folder…") appeared during setup, and its purpose was not clear. The user's conclusion: the app must become much simpler before more features. They also asked whether video belongs in the app, and whether it should be renamed *Image Workbench*.

**Assessment.** The architecture is sound, and the drive-containment traces and drive-failure checks exercised it end to end. What needs work is the presentation, the defaults, and one data-folder defect found on the same day (below). Video is not untestable here: setup and a 16-frame clip passed in three traced runs on the 6 GB card. Its limits are quality and time (about 3 minutes for a 2-second 512-pixel clip), not verification.

**Agreed priority 1: everything in one folder the user chooses (planned, not implemented).** The user decided (18 October 2026, evening) that Media Workbench must keep everything it writes in the single working folder the user chooses, so that nothing strays onto other drives and maintenance stays simple. This replaces the earlier decision to defer the "all-app-owned-files arrangement". Concretely:

- **No silent default on the system drive.** On first start the app asks where to work (suggesting the non-system drive with the most free space, never an excluded one) and writes nothing large until the user has chosen. Without a usable saved folder it says so and asks again, rather than falling back to `%LOCALAPPDATA%`. This also removes the defect class found on 18 October.
- **Preferences and the startup log live in the working folder.** Local AppData keeps only a tiny pointer to the folder's location, or nothing at all when the app is installed inside the working folder.
- **The installation can live in the working folder too** (for example `<folder>\App`). The installer offers this on first install, and updates keep it.
- **Development tooling too:** `scripts/test-publish.ps1` left one `MediaWorkbench-mcp-smoke-*` folder in `%TEMP%` per run (59 were found); it now removes its folder.
- **Already in place and traced:** temporary work, caches, update downloads, hand-overs and workers' bytecode stay inside the data folder (0.3.0-alpha.2 to alpha.11).
- **Acceptance:** a write trace of a fresh install, first start, setup, pictures, update and uninstall shows nothing app-owned outside the chosen folder except Windows' own bookkeeping (installer registration, Start-menu shortcut, crash reports), each listed in the docs.

**Agreed priority 2: simple model choice (planned, not implemented).**

- One **Models** view: a table of a few curated models, each with its name, what it is good for (in plain words), picture size, download size, an estimate of how long a picture takes on this computer (from measured timings), and a single action: **Get**, **Ready**, or why this computer cannot run it.
- Getting a model does everything else in the background: the private runtime on first use, the download, the checks and the GPU test.
- Create shows only a **Model** dropdown of ready models, each with its one-line description.
- Adding your own files or folders, Hugging Face search (Discover) and model removal move under **Advanced** in that view, in plain words.
- Better defaults, so a first picture is good: a recommended model chosen from this computer's hardware (an SDXL-family model where it runs acceptably, SD 1.5 otherwise), per-model step and size defaults, and a few plain style choices instead of raw sampler settings.

**Open decisions for the user (recommendations, not decided):**

1. **Video:** keep the existing, verified short-video feature but **freeze** it. No new video work until pictures are simple and good, and present it as one optional item ("Short clips, experimental") in the Models view rather than on the main path. Removing it would cut maintenance but discard working, verified code that is already isolated (`video.py`, `mw_encode_video`).
2. **Name:** keep **Media Workbench** for now. A rename touches the repository, the installer's identity (which upgrades depend on), the data and preferences folder names, the MCP server name and every document, and pictures plus upscaling plus optional clips still fit "media". If the focus becomes images only, change the display name later as its own small release.

**Defect found the same day (blocks 0.4.0-alpha.1):** the installed alpha.11 set up SD 1.5 and SDXL in the *default* data folder, `%LOCALAPPDATA%\MediaWorkbench\Data` on C: (13.2 GiB, leaving C: with 9.6 GB free). Yet `settings.json` named an existing D: folder with both models already verified. `SettingsStore.Load` reads that file correctly (checked with the built assembly), so the cause is not yet known. The default folder was created at 05:34 local time, after the settings file was last written (04:15). That folder had last been set during development and was never chosen in the app's Settings, so a development-only cause has not been ruled out. At the user's request that folder was then moved, verified file by file, to a folder on D:, which became the saved data folder; the C: copy was deleted. Next: launch the installed app, check which folder Settings shows, and reproduce from a fresh launch. The drive-containment traces did not catch this because they always passed an explicit data folder.

**Order from here:** (1) find the data-folder defect's cause, and fix it by removing the silent default (priority 1 above); (2) finish 0.4.0-alpha.1 with the one-folder arrangement and its trace, the interactive session, then release; (3) the simple-model-choice milestone (0.5.0); (4) quality defaults; and only then video, models of other families or other tools.

## Purpose and next feature priority

**Status, 18 October 2026:** development resumed after the pause. The [drive-containment milestone](storage-locations.md) is implemented in code (0.3.0-alpha.2 to alpha.4) and awaits its acceptance checks with the user present before it is called 0.4.0-alpha.1; alpha.5 to alpha.7 added faster repeated and image-to-image pictures, several versions per Generate, and SDXL fine-tunes; alpha.8 and alpha.9 added the picture queue (including adding while pictures are made) and a new seed for each Generate. The ordered list under [What to do next](#what-to-do-next) is current.

Media Workbench aims to move image and eventually video generation onto the user's own computer, with offline use after setup and less reliance on online generation services. Short videos (2–3 seconds) are implemented; longer and image-to-video clips are not. Energy, water, chip-demand, and cost benefits have not been measured; local generation still uses electricity and hardware. It stays free, MIT-licensed, and unlocked on the public repository. It must serve beginners as well as power users, so runtime, precision, and pipeline details stay under the hood behind plain choices.

The previous feature priorities, now implemented within the limits described, are:

1. **Add your own downloaded models.** Done for SD 1.5-family single files and Diffusers folders in 0.2.0-alpha.11; other architectures follow with their own verified profiles.
2. **Download models from Hugging Face.** Implemented for public root-level single-file SD 1.5 checkpoints in alpha.14: license/file hints, pinned metadata and bounded header checks, hardware/space/readiness limits, and download through native checks and real inference verification. Direct Diffusers-folder downloads, protected access and other model architectures remain separate verified slices.
3. **Newer image models and short video.** Implemented in 0.3.0-alpha.1 as optional verified setups: Stable Diffusion XL base 1.0 and 2–3 second AnimateDiff videos, each with its own download, native verification, real GPU test, and hardware-chosen runtime (streaming on 6 GB cards). SDXL fine-tunes, videos from added models, and image-to-video follow with their own verification.

## Path to 1.0.0

The user's 1.0 scope is text-to-image, image-from-image (restyle and painted changes), upscaling, newer image models where the GPU allows, and video, with check-then-ask updates and MIT licensing. All are implemented as of 0.3.0-alpha.1. What still stands between that and an honest 1.0.0:

1. **Real-hardware evidence for each setup on the development GPU**: done headlessly for the conservative video (`video-fp32-sequential`) and SDXL (`xl-fp32-sequential`) choices in 0.3.0-alpha.1 (see `docs/validation.md`); the GUI walkthrough of them remains part of item 3. Faster choices stay "verified per machine" until someone with that hardware runs the checks; that is acceptable for 1.0 because every machine must pass its own test before anything is ready.
2. **Clean-machine installer, upgrade and update checks** in Windows Sandbox or a spare Windows 10/11 machine (the user agreed to enable Sandbox): fresh install, upgrade from an alpha, offline launch after setup, Update now, uninstall keeping data.
3. **Interactive acceptance pass** of every page with the user available: keyboard navigation, narrow windows, high DPI/text scaling, the new video player and model choices, long operations and cancel.
4. **Stability under repeated use**: the durable queue is optional for 1.0, but generation must stay reliable across many runs; measure repeated load times (now recorded per job) and fix anything flaky.
5. **Release hygiene**: version 1.0.0 in `Directory.Build.props` with a changelog section, README and docs describing exactly what works, and no "alpha" wording left where it is no longer true.

Alongside these, every feature follows the product principles in `AGENTS.md`: easy to use, stable, aware of the computer it runs on, clean, and mindful of drive space. The section below says what that still requires.

## Standing principles: system awareness, clean-up, and drive space

`AGENTS.md` lists these as product principles for every feature. This is where the app stands against them and what to build.

**Already in place.** Setup checks the NVIDIA driver and the GPU's memory against the recipe's minimum, on the same device inference uses. Setup and adding a model check free space first. Settings → Storage shows free space and what each part of the data folder uses. Interrupted generations lose their partial image, unfinished record writes are removed, failed or interrupted model imports are deleted, painted-area hand-over files are deleted after use, and a failed update download is discarded. Download caches and logs can be cleared by hand, and automatic clean-up and free-space checks now follow the rules below.

**System awareness — done in 0.2.0-alpha.13, verified on one GPU.** A hardware profile (GPU name, compute capability, graphics memory, driver, system memory, data-drive free space and type) is read once per data folder per session without loading an AI runtime and shown in plain words in Diagnostics and on Create's setup card. It chooses one of four runtime choices (half or full precision, whole model on the GPU or offloaded), the upscaler tile size from free graphics memory, and refuses or warns plainly when memory is too small. Each runtime choice has its own readiness stamp and must pass the real GPU test; a failed faster choice falls back to the conservative `fp32-offload` and is not retried on the same card and driver. Drive information now uses Rust's `mw_drive_info` through the storage adapter; the duplicate Python implementation is removed. Diagnostics shares the ordinary installation-readiness checks and does not call missing or changed files verified. Still open: real-hardware validation of the three faster choices (item 1 under What to do next).

**Clean-up — done in 0.2.0-alpha.12.** Rust's `mw_tidy_data_folder` owns the rules and runs under the data-folder lock at startup and after a verified setup: unfinished-job records beyond the 50 Library lists (with their inputs and logs), logs beyond 300 or 30 days (never an unfinished job's), setup downloads left unfinished for 72 hours or after verification, and the download caches once setup is verified unless Settings keeps them. The desktop sweeps painted-area hand-overs and finished update installers from the data folder's `temp/` (and, from earlier versions, `%TEMP%`); Rust removes crashed workers' `temp/work` folders. Still open: pruning Library images themselves needs the organization and provenance export described under Later expansion first.

**Drive space and speed — done in 0.2.0-alpha.12; load timing in 0.2.0-alpha.16.** Generation and upscaling check free space before writing; Create, Tools, and Settings warn below 5 GiB; `mw_drive_info` detects a hard disk, USB, or network data folder and Create and Settings say that models load faster from an SSD and the folder can be moved. Each generation now records its model-load time and, when loading was slow, a plain note naming the slow drive or a busy one. Still open: calibrating those thresholds on real hard-disk/USB folders.

Acceptance: routine tests cover profile selection from fake hardware descriptions, each clean-up rule including what it must keep, crash leftovers, and low-space refusal before any write (all in place); opt-in GPU checks verify each runtime choice on real hardware (only `fp32-offload` so far).

## Immediate validation

Exercise the current installer and complete image workflow in clean Windows 10 22H2 and Windows 11 environments. Cover install, upgrade, uninstall/data preservation, offline launch after setup, and the app's update/relaunch sequence. Check the Library search, paging, settings reuse, save picker overwrite/cancel behavior, default image viewer, high DPI, narrow windows, and keyboard navigation. ## Expand the native core

Artifact export, storage inventory, and pinned model-file verification are now Rust services. Inventory/export are called directly by the desktop/MCP/CLI; setup uses a thin Python adapter for model-file verification. Continue moving owned-storage pruning, artifact/job validation and indexing, durable queue state, and bootstrap/package verification into narrow, documented C ABI services. Keep path containment, atomic commit, cancellation, and file ownership inside Rust with meaningful boundary tests. C# should own presentation and host coordination; Python should focus on Hub integration, runtime provisioning, and the ML libraries that require it. Avoid adding a second implementation of domain policy in each client.

## LLM tool access

The local stdio MCP host is now implemented; see [LLM tools](llm-tools.md). Continue validating real clients and design authenticated remote access so a cloud-only LLM client can inspect the installation, plan/setup the supported model, and submit image/upscale jobs. The LLM client handles its own provider account; the application should not collect or embed provider account tokens. An account alone does not guarantee that a particular client supports local tools.

The implemented stdio host uses the existing C# service and Windows Job Object ownership. Require an explicit data folder, default to inspection tools, and grant setup downloads and GPU generation only through launch-time capabilities the model cannot enable for itself. Keep model IDs/runtime profiles constrained to the verified bundled recipes. Reuse the normal native plan and inference/readiness gates, bounded JSON messages, cancellation, and durable records. Tool outputs must describe actual installed/verified state and explicitly report that video is unsupported.

A cloud-only client needs an authenticated remote transport or a trusted local connector. Do not equate a local stdio server with an Internet-accessible endpoint. A later remote service needs scoped authorization, authenticated sessions, origin checks, TLS, auditing, and durable long-running job handles; it must not expose arbitrary shell execution, provider credentials, or unrestricted file access. See the official [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) and [tool protocol](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

## Durable generation queue

Start with the existing job JSON as the authoritative store. Persist a queued job's complete settings and private input copy before acknowledging it. Distinguish queued, running, succeeded, failed, cancelled, and interrupted states. An explicit queue owner must claim work under the data-folder lock; separate clients must never run simultaneous GPU jobs in the same folder. Removing a pending item must not delete an already completed image. A failed job must not discard later queued items.

Pending work should be visible after a restart and require an explicit Resume action; do not start GPU work merely because Library was opened. Cancellation must distinguish cancelling the active job from removing pending work. Closing/crashing the app must still kill the owned process tree, and recovery must mark its active job interrupted without converting pending jobs to failed work.

The current global `IsBusy` and one-request-per-worker transport are deliberate limitations. Introduce separate inference/maintenance and browsing state before allowing enqueue or Library actions during generation. Folder changes, setup, installation removal, and updates must coordinate with the queue owner. Retain a clear UI representation of which saved folder owns pending jobs.

Acceptance checks: atomic enqueue and claim, input copies surviving source removal, restart without automatic inference, multiple-client exclusion, active versus pending cancellation, failure followed by another job, crash recovery, data-folder changes, and unchanged readiness gating. Keep routine tests free of model downloads and hardware requirements; use opt-in real GPU checks for the complete lifecycle.

## Then evaluate a warm inference worker

Measure model-load/import time separately from inference on the existing verified profile before choosing an idle policy. Keep the ML runtime in a child process owned by the same Windows Job Object; the GUI must never load PyTorch or Diffusers. Reuse a pipeline only for the same verified profile, model stamps, GPU selection, precision, and operation-compatible configuration. Sampler and image-to-image changes must not leak state into the next job.

Cancellation or protocol failure may discard the warm child and recreate it for the next queued job. Release it before install/verify, removal, saved-folder changes, updates, or shutdown, and after an explicit idle timeout. Account for retained CPU/GPU memory on 6 GB devices. A crash must still produce an interrupted active job and no partially committed Library image. Changes to inference loading or verification semantics require an adapter-version bump and fresh real inference checks.

## Later expansion

Add Library organization and portable settings/provenance export before destructive artifact pruning. Any deletion needs precise image/job/source relationships so a reused private input is not removed accidentally. Extend model adapters (including a dedicated inpainting checkpoint if quality requires it), protected Hub access, other hardware, and video only with explicit runtime/license/hardware validation. Discovery results must continue to describe metadata without implying installation support.
