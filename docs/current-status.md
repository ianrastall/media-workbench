# Current implementation status

Version: **0.3.0-alpha.3**. Development started 17 October 2026.

**Drive containment, in progress (18 October 2026).** The release milestone is [drive containment](storage-locations.md), intended as 0.4.0-alpha.1 after implementation and validation. **Slice 1 implemented (unreleased, after 0.3.0-alpha.1):** app-owned temporary work now lives in the saved data folder's `temp/` folder. Each Python worker gets `temp/work/<id>` as its `TEMP`/`TMP`/`TMPDIR`; setup and GPU children get their own folder there, and NVIDIA's compiled-kernel cache (`CUDA_CACHE_PATH`) and `TORCH_HOME` move under `cache/`. Painted-area hand-overs (Create and MCP) use `temp/painted`, and update installers download to `temp/updates` after a free-space check. A data folder that is missing, unwritable, or reached through a junction stops the operation with a plain explanation; nothing falls back to Windows temp. Read-only operations (health, hardware profile, Hub search/details, model inspection) still never create a missing data folder. Crashed workers' folders are removed by Rust clean-up unless a live worker holds them open, and the old `%TEMP%` locations are only swept. Headless checks only; no process-write trace or GPU run has been made with these changes. **Slice 2 implemented:** Settings has **Where Media Workbench keeps things**, listing the data folder, its `temp/` and `cache/` folders, the preferences/startup-log folder and the app folder, each with the volume it is really on (Rust `mw_drive_info` now returns the mount point from `GetVolumePathNameW`, so mounted folders are named correctly) and one sentence saying what, if anything, is on another drive. Still outside the data folder: preferences and the startup log (Local AppData, about 2 MB at most), the default installation, and the installer's own extraction. **Slice 3 implemented (0.3.0-alpha.3):** Settings → **Move my data there…** checks the typed folder with Rust `mw_plan_data_move` (files and bytes to copy, free space with a 1 GiB reserve, same-volume note, and plain blockers: inside/containing the data folder, not empty, a link inside the data folder, not enough space), then **Move now** runs `mw_move_data_folder`: under the data-folder lock it copies everything except `.operation.lock`, `temp/`, `library/` (rebuilt) and `.removing/` into a marked `.<name>.moving` staging folder, hashes each file while reading, re-reads and compares the copy, keeps modification times (readiness stamps compare size and time), re-checks free space before every file, and renames the staging folder into place last. Only then are settings switched. The old folder is never changed; the app says it can be deleted in File Explorer once the new one is checked. Failure or cancellation removes the staging folder; a crash is recovered at the next start from `PendingMove` in preferences. Readiness carries over because the bytes and times are identical and the runtime, job and readiness records hold no absolute paths (checked on the development data folder); no GPU run after a real move has been made yet. **Removing the old copy (unreleased):** after a move, Settings offers **Remove the old copy…** (with a confirmation flyout; remembered across restarts as `MovedFrom`). Rust `mw_remove_moved_data` holds the old folder's lock and deletes only files whose copy in the current data folder has the same size and modification time, plus the old folder's own `temp/`, `library/` and `.removing/`, then empty folders, the lock file and the folder itself if empty. Files that differ or were added later are kept and counted. Saving a different folder forgets the old copy. **Slice 4 implemented (unreleased):** Settings lists **Drives on this computer** (ready fixed, removable and network drives, with quota-aware free space and type from Rust, and which one holds Windows); **Use this drive** fills in `<drive>\Media Workbench` without saving or moving. Before the first Install / verify, when the data folder is still the default on a drive with less free space than another non-network drive and was never chosen, Create asks where to work and setup waits until the user keeps the drive or saves another folder. The choice is remembered (`DataRootChosen` in preferences); folders saved by earlier versions count as chosen, and a ready installation is never asked. Installer: Inno Setup already reuses the previous install folder on upgrade (`UsePreviousAppDir` default) and shows the destination page only on first install (`DisableDirPage=auto`); its own unpacking uses Windows temp briefly. No installer change was made in this slice. Volume restrictions, the all-app-owned-files arrangement, clean-machine installer checks, and a real write trace remain.

The documentation checkpoint passed the existing headless check suite and a separate-output Debug build; [validation](validation.md#storage-milestone-planning-checkpoint) records the commands and limits. Those checks do not establish drive containment.

## Technology decisions

0.3.0-alpha.1 adds two optional verified setups beside Stable Diffusion 1.5, sharing one helper (`workers/python/addon.py`): short AnimateDiff videos (`video.py`) and Stable Diffusion XL base 1.0 (`sdxl.py`). Each has pinned files, native verification, its own hardware-chosen runtime table with a conservative streaming fallback for 6 GB cards, a real GPU test, and a readiness record that also requires the base installation. Rust gains `mw_encode_video` (H.264 MP4 through Media Foundation, loaded at call time) and MP4 export. See [inference](inference.md#stable-diffusion-xl) and [short videos](inference.md#short-videos).

Alpha.16 times runtime start, model loading and inference separately in the ML child and stores them in every job record. The coordinator adds a plain `loadNote` when loading was slow for the data folder's drive (Rust `mw_drive_info` supplies the kind; the rule is `hardware.load_note`), and Create shows both after saving. Inference settings, adapter versions and readiness stamps are unchanged; the rule is not yet calibrated against a real hard-disk folder.

Alpha.15 moves SD 1.5 tensor-layout compatibility into Rust through additive ABI 1 `mw_check_model_compatibility`. Local checkpoints, local Diffusers parts, pinned Discover headers and copied-model rechecks share the policy and its plain refusals. Python still performs bounded safetensors structural/offset checks, folder configuration checks and orchestration; ML stays out of process. File/runtime/real GPU gates and existing readiness stamps are unchanged. Copied Diffusers parts now repeat weight-format checks as well as shapes. See [validation](validation.md) and [handoff](../HANDOFF.md); routine work is headless, with desktop control announced only when an interactive check requires it.

| Layer | Selected implementation |
|---|---|
| Windows UI | WinUI 3, dark theme, custom title bar, DPI-aware initial sizing |
| Presentation | CommunityToolkit.Mvvm, observable partial properties, commands |
| Managed language/runtime | C# 14, .NET 10 |

The small metadata/setup worker has no machine-learning packages. An independently provisioned Python 3.12 child loads a locked PyTorch CUDA 12.6 / Diffusers profile. No AI runtime enters the GUI process.

## Implemented

**Short videos** (Create → What to make → A short video): 16- or 24-frame clips at 8 frames a second from the bundled SD 1.5 with the pinned AnimateDiff motion adapter v1-5-3. **Set up videos** downloads the adapter (1.7 GB), verifies it natively, and runs a real 16-frame clip on the GPU encoded to MP4 before `jobs/install-video.json` is ready; runtime choices `video-fp16-model`, `video-fp16-sequential`, `video-fp32-model`, and the conservative `video-fp32-sequential`. The ML child safety-checks every frame on the CPU and writes raw frames and a poster; Rust's `mw_encode_video` writes `video.mp4`. Library filters, plays and exports videos; Create loops the latest one. Clean-up, recovery, storage removal and MCP (`workbench_video_status`, `workbench_install_video`, `workbench_generate_video`) cover them.

**Stable Diffusion XL** (Create → Get Stable Diffusion XL): pinned SDXL base 1.0 fp16 files (6.9 GB) downloaded by the ML child, verified natively, and tested with a real 1024 × 1024 picture before `jobs/install-sdxl.json` is ready; runtime choices `xl-fp16-model`, `xl-fp16-sequential`, `xl-fp32-model`, and the conservative `xl-fp32-sequential`, with full precision refused below 16 GB of system memory. It joins the Model chooser with its own sizes, supports starting pictures and painted changes, and is reviewed by SD 1.5's safety checker. Settings removes either setup and keeps what was made.
Live public model search and details, native planning and SHA-256, worker health, storage settings, visible errors/cancellation, session activity, application identity, singleton launch, Start menu integration, and installer build/publish scripts. The GUI uses real view-model commands rather than implementing operations in click handlers. View code handles navigation, title bar, and window geometry.

Create provisions a private Python/uv runtime and hash-locked wheels, fetches selected SD 1.5 safetensors/configuration files at an immutable Hub commit, verifies all model SHA-256 values, and tests actual 512 × 512 CUDA inference before recording ready state. It supports a prompt, negative prompt, seed, 1–50 steps, guidance 1–20, square/portrait/landscape sizes (512 × 512, 512 × 768, 768 × 512), a sampler (the model's PNDM default, DPM++ 2M Karras, or Euler ancestral), image-to-image from a chosen, dropped, or Library picture with three change levels, painted partial changes (inpainting) of that picture, progress/cancel, PNG preview, and durable settings/output evidence. Library searches prompts, negative prompts, seeds, and job IDs, filters generated/upscaled images, and pages through all matching successful images (48 per page) in a virtualized grid with thumbnail-size decoding. A rebuildable SQLite index reads changed JSON records on refresh; image paths and existence are rechecked. Use settings restores a successful image in Create or Tools, including its private starting picture. Open image uses the default PNG viewer; Save a copy calls Rust directly for job validation, filesystem containment, cancellable streaming/hash verification, and atomic export, via the native Windows App SDK picker, verifying the recorded checksum before atomically replacing the destination outside the managed data folder. Both actions are available on the latest Create/Tools result too. Library also shows up to 50 recent failed, cancelled, or interrupted generations with their reason, a button to reuse their settings in Create, and their own inference log when one exists. Settings edits a draft folder path that takes effect only when saved; every operation uses the saved folder. Tools upscales a chosen, dropped, or Library picture 2× or 4× with Real-ESRGAN x4plus (weights pinned by SHA-256, verified on the GPU during Install / verify), saving the result to Library. Home checks GitHub Releases (at startup when online, unless turned off, and on request), shows the newer version's notes, and on **Update now** downloads and SHA-256-verifies the installer, releases the single-instance mutex, runs it silently, and exits; the installer reopens the app. Runtime and model components follow the app: a version that changes the pinned profile asks for Install / verify, which downloads only what changed. Its Storage section measures each part of the data folder and, after confirmation, clears download caches or logs or removes the SD 1.5 runtime, model, and caches while keeping images and job records. Setup attempts survive restarts and can be retried with retained downloads. Each worker process tree is owned by a kill-on-close Windows Job Object, so an app crash or forced stop cannot leave the inference child running, and generation jobs orphaned by a crash are recorded as interrupted. See [inference lifecycle](inference.md).

The installer also includes a self-contained local MCP stdio console host. Settings generates configuration for a compatible LLM client, scoped to the saved data folder. It defaults to inspection; launch-time flags separately permit bundled-model setup and verified generation/upscaling. The client owns its provider account; the model cannot change the folder or enable permissions. It returns image paths/settings rather than image bytes. The host uses the same C# worker supervisor and kill-on-close Job Objects. [MCP setup](llm-tools.md) describes the supported tools, privacy, and transport limits.

Release builds generate the main README's version/date, release links, and changelog summary before committing; checks and the release job reject stale summaries. GitHub Actions publishes the checked installer, its SHA-256, and a generated release README. The release body includes current installation requirements, features, MCP guidance, licensing, and checksum steps from the public README with version-pinned documentation links. The public repository also has relevant GitHub topics and a descriptive summary.

Rust owns storage inventory, export, and pinned model-file verification. Inventory includes cancellable traversal, logical bytes/file counts, installation totals, and Windows available disk space. Desktop, MCP, and CLI inspection call inventory directly without Python; worker clients use a thin adapter. The supported profile/model IDs come from the bundled storage layout. Links/reparse points are rejected in managed area ancestors and skipped inside trees; access failures do not produce partial totals. Removal retains the existing confirmed, locked worker implementation and readiness invalidation.

Install / verify calls the native pinned-file verifier through a thin Python adapter. It validates contained paths, sizes, SHA-256, and unchanged metadata, uses read-only sharing on Windows to refuse concurrent writers/deletion, and checks cancellation every 64 KiB with throttled byte progress. Existing size/mtime readiness stamps are preserved. The runtime and actual GPU inference tests remain mandatory; no inference profile or adapter-version change is needed for moving the same file checks into Rust.

**Paint the part to change** turns a starting picture into a painting surface (three brush sizes, erase, clear). The painted area is a UI-free Core grid with the picture's EXIF-oriented proportions (at most 512 cells a side), handed to the worker as a grayscale PNG and kept as the job's private `mask.png`. The ML child redraws a box around the paint with added context at the nearest supported shape using Diffusers' inpainting pipeline on the same verified SD 1.5 weights, then blends it back with a softened edge into the full-size picture (up to 4096 pixels on the longest side); unpainted pixels keep their values. **Use settings** restores the picture, painted area, and change level. MCP clients can describe a rectangular change area instead of painting.

**Add a model you already downloaded** (Create, once the bundled model is ready) accepts an SD 1.5-family single-file `.safetensors` checkpoint or a Diffusers folder. A standard-library worker module identifies it from safetensors headers alone (UNet input/output and cross-attention shapes, CLIP text width, VAE shapes, weight types, and that the header describes the whole file) and refuses other architectures, add-ons, damaged or incomplete files, quantized weights, and pickle files with a plain reason; model code and the user's configuration files are never used. Rust's new `mw_import_file` copies each file into `models/imported/<id>/` in one hashing pass with read-only source sharing; the copy is then verified natively, re-identified, checked for duplicates, and tested with the same 512 × 512 GPU inference check as the bundled model, reusing its runtime, tokenizer, scheduler, safety checker, and configuration (and its VAE when the model has none). Copying keeps the verified bytes in the managed, link-free folder, so the original can move or be deleted without breaking a ready model; nothing is kept when any step fails. A ready model needs its own unchanged stamps, the current adapter version and profile stamp, and a ready bundled installation. Create's **Model** chooser appears only when an added model is ready; job records store `settings.model`, `model`, `modelName`, and a local source description, Library names the model, and **Use settings** restores it (falling back to the bundled model with a note). Painted changes, image-to-image, and upscaling work with either. Settings → Storage measures added models separately, lists each with **Test again** and confirmed **Remove…** (images, jobs, and originals kept). MCP lists models (`workbench_models`) and generation can name a ready one; adding or removing models stays in the app.

**This computer** (Create's setup card and Diagnostics) shows the NVIDIA GPU with its memory, compute capability, and driver, system memory, and the data folder's free space and drive type, read by the standard-library worker (`system.profile`), with drive information supplied by Rust's `mw_drive_info`, without loading an AI runtime and once per data folder per session. Diagnostics uses the same file/runtime readiness checks as installation status and withholds the verified label for a card that cannot use the tested runtime. From it the worker chooses one of four runtime choices — `fp16-gpu`, `fp16-offload`, `fp32-gpu`, or the conservative `fp32-offload` — by whether half precision is trusted on the card (compute capability 7.0 or newer, excluding Turing cards without tensor cores such as the GTX 16-series) and how much graphics memory it has. Setup refuses less than 8 GB of system memory or a GPU under the recipe's 6 GB with a plain reason, and warns below 16 GB when the model waits in system memory. The chosen runtime must pass the real GPU test during Install / verify; a failure falls back to `fp32-offload` and is remembered for that card and driver. The verified runtime is part of the readiness stamp (`ADAPTER_VERSION` 3) and of each added model's record (`IMPORT_ADAPTER_VERSION` 2); the ML child re-checks it against the card it sees before loading. Create notes when faster settings could be tested, or when the card changed. Upscaling picks its tile size from free graphics memory and halves it if memory still runs short. Only `fp32-offload` has passed on real hardware so far; see [inference](inference.md#hardware-profile-and-runtime-choice) and [validation](validation.md).

**Clean-up and drive space.** Rust's `mw_tidy_data_folder` applies every automatic removal rule under the data-folder lock, so it never races setup, generation, a model import, or a removal (it reports the folder busy instead and the next start tries again). The desktop runs it at startup and the worker after a verified Install / verify. It keeps the newest 50 failed, cancelled, and interrupted job records (exactly the ones Library lists) with their private inputs and logs and removes older ones with theirs, never a finished image; keeps logs to the newest 300 and the last 30 days, never removing the log of a running or listed unfinished job; expires setup's `.partial`/`.incomplete` downloads after 72 hours, or once setup is verified; and, after a verified setup, removes the `cache/` and `bootstrap/` download caches (about 4 GiB) by renaming them into `.removing/` first, so a crash mid-removal is finished next time. Settings → Storage explains this and has **Keep setup's download files for repairs** (off by default). It also removes `temp/work/<id>` folders of workers that crashed (a running worker's open owner file protects its folder). The desktop removes painted-area hand-over files a crash left in `temp/painted`, installers of a finished update and interrupted installer downloads in `temp/updates`, the same leftovers from earlier versions in `%TEMP%`, and bounds its startup error log. Images, succeeded and damaged records, **Use settings** pictures, added models, and unrecognized files are never removed. Generation and upscaling check free space under the lock before writing anything, sized for the largest picture the job can save, and refuse with the free and needed sizes and how to fix it. Rust's `mw_drive_info` reads free space and drive kind (SSD, hard disk, USB, removable, network) without creating the folder; Create, Tools, and Settings warn below 5 GiB free, and Create (once set up) and Settings say when the data folder is on a hard disk, USB, or network drive that models load faster from a solid-state drive and that the folder can be moved in Settings. After each picture, Create reports the model-load time apart from inference, and when loading took 20 seconds or more it names the slow drive, or on a solid-state drive says the drive or computer was busy (see [load time](inference.md#load-time-versus-inference-time)).

Builds centralize NuGet versions in `Directory.Packages.props`, commit per-project dependency locks, and require locked restores in CI. The .NET SDK baseline is 10.0.113 with patch-only roll-forward. Native hosts compile as x64 and reject conflicting platform/runtime choices; the Rust DLL loads only beside the executable. Published smoke checks inspect PE headers for the app, MCP host, Rust core, .NET runtime, and Python. [Stack alignment](stack-alignment.md) records deliberate exceptions and open evidence; [handoff](../HANDOFF.md) records exact resume commands.

Normal source builds also copy the console host beside the GUI for Settings-generated MCP configuration; published builds already bundle it with the runtime.

**Discover download and test.** Search adds license metadata and a file-availability hint. **Check model** fetches an immutable repository revision with file sizes/LFS SHA-256 metadata; Rust's `mw_plan_hub_model` permits bounded, complete root-level safetensors candidates with public access and a stated license. The worker reads at most an 8 MiB header at that revision and reuses local-import structural checks to reject unsupported architectures, add-ons and damaged files without downloading full weights. It also checks this computer's GPU/memory profile, free space and verified bundled runtime. The smallest candidate is checked by default; another may be selected under **Advanced options**. Search hints do not imply compatibility or readiness.

**Download and test** requires reviewing the pinned card/license, then re-fetches that exact revision and checks the reviewed file size/hash. It downloads one copy directly into an owned import folder, streams size/hash checks with responsive progress/cancel and repeated quota-aware free-space checks, retains bounded pinned model-card/license/notice files with Git-blob hash checks, and reuses native file verification and the existing real GPU test. Only then is the model ready and selected in Create. Failed/cancelled first additions are removed; existing import recovery removes crash leftovers. Repository, revision, file hash and license metadata are retained in the model and generated-job source. This uses the existing adapter/profile stamps, so alpha.13 models do not need re-verification. Local Diffusers folders remain supported; downloading them directly from Discover and authenticated Hub access remain planned. MCP retains its existing bundled-only setup capability and gains no arbitrary-download tool.
