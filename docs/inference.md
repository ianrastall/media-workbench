# First inference pipeline

The desktop app coordinates one SD 1.5 recipe. SD 1.5-family models added from [local files](#models-you-added) or [pinned Discover downloads](#discover-downloads) share its runtime. Search metadata never grants model readiness, and repository code is never executed. The recipe is experimental; each machine must pass inference verification before it is ready.

## Runtime boundary

```mermaid
sequenceDiagram
    participant UI as WinUI / MVVM
    participant Core as C# service + Rust plan
    participant Setup as Discovery Python 3.14 child
    participant ML as Private Python 3.12 child
    participant Disk as Selected data folder
    UI->>Core: Install / verify
    Core->>Core: Validate pinned recipe through C ABI
    Core->>Setup: installation.run (JSON lines)
    Setup->>Disk: Acquire lock; save attempt
    Setup->>Setup: Verify Python/uv archives; sync locked wheels
    Setup->>ML: Download selected files using Hub SDK
    ML-->>Setup: Progress
    Setup->>Disk: Check all model sizes and SHA-256
    Setup->>ML: Verify real 512 × 512 CUDA inference
    ML-->>Setup: GPU, precision, time, memory evidence
    Setup->>Disk: Atomic ready record
    Setup-->>UI: Terminal result
```

The bundled discovery interpreter remains independent of the ML runtime. Official CPython 3.12.10 embeddable x64 is extracted under `runtimes/sd15-cu126-v1/python`. Its isolated path file adds only its private site-packages directory. A checksum-pinned uv executable installs wheel-only packages into that directory. No system Python, PATH, global pip environment, or CUDA toolkit is modified.

The ML child uses `-I -u` and a closed stdin rather than inheriting the coordinator's protocol input. Python user-site packages and inherited Python configuration are excluded. Child output/diagnostics are saved under the data folder's `logs/` directory; only parsed progress and terminal events reach the GUI protocol. CPython 3.12.10 is the final official 3.12 maintenance binary; moving to a newer security-patched Windows runtime is a separate profile update, not an automatic untested interpreter replacement.

`profiles/sd15-cu126.in` records direct dependencies; `.lock` records exact transitive versions and hashes. PyTorch's CUDA 12.6 wheel is an immutable URL with a pinned SHA-256. uv is invoked with hash enforcement, no configuration discovery, an explicit interpreter, an owned cache, and no source builds. Inherited pip/uv configuration variables are excluded. See [uv hash checking](https://docs.astral.sh/uv/reference/settings/#require-hashes) and [official PyTorch builds](https://pytorch.org/get-started/previous-versions/).

`profiles/sd15-files.json` selects 16 files, approximately 2.55 GiB, from model commit `451f4fe16113bff5a5d2269ed5ad43b0592e9a14`. It excludes pickle checkpoints and duplicate full-precision weights. The supported Hub SDK handles selected-file downloads and its local cache. Each selected file has a checked size and SHA-256 before inference. Public requests explicitly disable implicit account tokens. Review the [model card and license](https://huggingface.co/stable-diffusion-v1-5/stable-diffusion-v1-5).

## Execution and evidence

The inference child uses the built-in `StableDiffusionPipeline`, safetensors, local files only, and offline environment flags. Model files cannot select custom remote Python code. The safety checker remains enabled, and VAE slicing is always on. Precision and model placement come from the hardware profile below. See [Diffusers memory management](https://huggingface.co/docs/diffusers/en/optimization/memory).

### Hardware profile and runtime choice

`workers/python/hardware.py` (standard library only) reads the hardware without loading an AI runtime: the GPU the ML child will use (`nvidia-smi` name, total and free memory, compute capability, driver; drivers older than R510 that cannot report compute capability are asked again without it), total and available system memory (`GlobalMemoryStatusEx`), and the data folder's quota-aware free space and drive type (Rust's `mw_drive_info` through the storage adapter; the nearest existing folder is read and nothing is created, with no duplicate Python drive detection). The worker operation `system.profile` returns it with the chosen settings, the settings the installation was verified with, and a plain note; the GUI reads it once per data folder per session (again after Install / verify and on **Run diagnostics**) and shows it on Create's setup card and in Diagnostics.

Each runtime choice is a separate verified profile:

| Runtime | Computation | Model placement | Chosen when |
|---|---|---|---|
| `fp16-gpu` | float16 | whole pipeline on the GPU | half precision is trusted and at least 8 GB of graphics memory |
| `fp16-offload` | float16 | model CPU offload | half precision is trusted, 6–8 GB |
| `fp32-gpu` | float32 | whole pipeline on the GPU | half precision not trusted, at least 10 GB |
| `fp32-offload` | float32 | model CPU offload | everything else; the conservative fallback |

Half precision is trusted on compute capability 7.0 and newer, except Turing cards without tensor cores (compute 7.5 without "RTX" in the name, other than the Tesla T4): GTX 16-series, Quadro T-series, and MX cards produce blank or broken images in half precision, so they keep `fp32-offload`. An unknown compute capability is never trusted. Memory limits allow 128 MiB below the nominal size for graphics memory and 1 GiB for system memory, because drivers and Windows report slightly less than installed. Setup refuses, in plain words, a GPU below the recipe's `minimumVramMiB` (6144) or less than 8 GB of system memory, and warns below 16 GB when the chosen runtime keeps the model in system memory.

Install / verify tests the chosen runtime with the real GPU test. If it fails (for example a blank image or running out of memory) and is not the conservative choice, the failure is recorded in `declinedRuntimes` (runtime, GPU name, driver, adapter version) and `fp32-offload` is tested instead; a later Install / verify on the same card and driver skips the declined choice, and a driver update retries it. Cancellation or a failing conservative test never produces a ready record. The ready record stores `runtime`, and the readiness stamp includes it (`profile_stamp(app, runtime)` hashes the adapter version, the runtime's precision and offloading, and the pinned files), so each choice is verified on its own and changing the table invalidates readiness. Generation passes the verified runtime to the ML child, which checks it again against the device CUDA reports (name, compute capability, memory) and refuses settings that do not suit that card, so a swapped GPU cannot run untested settings; job records store the `runtime` and the child reports `precision` and `offload`. When the computer could use faster settings than the verified ones (for example after a GPU upgrade), Create shows a note suggesting Install / verify; when the verified settings no longer suit the card, it says to verify again.

Before taking the data-folder lock, the coordinator passes the recipe through the Rust installation gate (`mw_plan_installation`, loaded with `ctypes` from the app's `media_workbench_core.dll`), so a blocked recipe never starts an attempt whichever client asked. A fresh setup requires 20 GiB free; once the runtime is recorded as synced against the current lock, re-verification requires only the size of missing model files plus 2 GiB. Setup requires free space, NVIDIA device detection, CUDA availability, and the recipe's `minimumVramMiB` (6144). Setup (via nvidia-smi) and the inference child (via CUDA) apply that same limit, with a 128 MiB allowance because drivers report slightly less than nominal capacity, to the same device: the child runs with `CUDA_DEVICE_ORDER=PCI_BUS_ID`, so its `cuda:0` is the first `CUDA_VISIBLE_DEVICES` entry (or nvidia-smi index 0) that setup inspected. A missing or unreadable memory value such as `[N/A]` fails setup with an explanation. Verification renders a fixed 512 × 512 prompt with four inference steps, checks output dimensions and image variation, and rejects safety-filtered output. The ready record includes the verified runtime choice, GPU name, Torch/CUDA versions, precision, offloading, inference duration, peak allocated GPU memory, UTC timestamp, the size and modification time of each verified model file, and a readiness stamp. The stamp covers an explicit `ADAPTER_VERSION` in `inference_setup.py` (3 since the runtime choice was added), the runtime choice, and the profile, lock, file manifest, and recipe with line endings normalized; editing worker source does not revoke readiness, so changes that alter what verification means must bump the adapter version. This is a smoke test, not a performance certification or guarantee for every prompt or driver.

Generation accepts guidance from 1 to 20, a size of 512 × 512, 512 × 768, or 768 × 512, and a sampler: `pndm` (the model's own scheduler), `dpmpp-2m` (DPM++ 2M with Karras sigmas), or `euler-a` (Euler ancestral); the coordinator rejects anything else before touching storage. With an optional starting picture (PNG, JPEG, WebP, or BMP up to 50 MB) and a strength of 0.05–1, generation runs `StableDiffusionImg2ImgPipeline` on the same verified weights. The coordinator copies the picture to `artifacts/<id>/source.<ext>` before inference and records only that relative copy, never the original location; the child applies EXIF orientation, picks the supported shape nearest the picture's proportions, and center-crops to it. With a painted area as well (`maskImage`, a PNG whose grid must match the picture's proportions within rounding), generation changes only that part: the coordinator keeps a private `artifacts/<id>/mask.png`, and the child scales the mask to the oriented picture, takes its painted bounds, adds context (a quarter of the painted size, at least 32 pixels), grows the box to the nearest supported shape and to at least 384 pixels where the picture allows, and redraws that crop at the shape's size with `StableDiffusionInpaintPipeline`, which blends the standard 4-channel UNet's latents outside the slightly grown mask at each step. The result is resized back and pasted through a feathered mask, so the output keeps the picture's full size (at most 4096 pixels on the longest side) and unpainted pixels outside the feather keep their values. Strength levels for painted areas are 0.5, 0.75, and 1 (replace). Image-to-image and painted changes are not part of per-machine verification, which still renders text-to-image at 512 × 512. Upscaling (`upscale.image`, scale 2 or 4) shares the readiness gate, job records, private input copy, and Library listing. The ML child builds the RRDBNet layout in `upscaler.py`, loads the pinned `RealESRGAN_x4plus.pth` with `torch.load(weights_only=True)` and strict key matching, and enlarges in tiles with 16 pixels of overlap, always in float32. The tile edge follows the graphics memory free after loading the upscaler: 512 pixels with at least 5 GiB free, 384 with 3 GiB, 256 with 1.5 GiB, otherwise 128; if the card still runs out of memory the tile is halved down to 128 before the job fails with a plain message. Measured on a GTX 1660 Ti with a 768 × 512 picture, peak allocation was about 0.3, 0.75, 1.5, and 2.4 GiB for 128-, 256-, 384-, and 512-pixel tiles, and larger tiles were only about 10% faster; the job record stores the tile used. 2× is the 4× result resized with Lanczos. Inputs are limited to 2048 pixels on the longest side. Install / verify downloads the weights with the coordinator's checksum-verified downloader, includes them in full SHA-256 verification and size/mtime stamps, and runs a 64 × 64 → 256 × 256 enlargement on the GPU; `ADAPTER_VERSION` 2 marks that change. Generation checks the matching readiness stamp and compares each model file's size and modification time with the values recorded at verification (full SHA-256 runs only during install / verify), validates inputs, starts an isolated inference child, and forwards per-step progress. A PNG is written under a unique artifact directory and finalized by atomic rename. Only then is the job marked succeeded. The job JSON stores the image path relative to `artifacts/` (`<id>/image.png`), the prompt, negative prompt, seed, steps, size, guidance, sampler, model recipe/profile, output SHA-256, device, and timing. Seeds reproduce settings; identical pixels across different drivers/hardware are not guaranteed.

Pinned model-file verification is a Rust service (`mw_verify_file`) behind a thin Python adapter. It checks safe contained paths, expected file sizes and SHA-256, and stable metadata; Windows read-only sharing refuses concurrent writing/deletion while hashing. Byte progress is forwarded with throttling, and cancellation is checked every 64 KiB, including within multi-gigabyte weight files. The coordinator retains its pre/post size/mtime stamp checks. Cancelling keeps downloads for retry and cannot mark setup ready. This changes the implementation of the existing file proof; the inference profile, GPU checks, and readiness-stamp format stay the same.

## Discover downloads

As of alpha.15, local and remote tensor-layout compatibility is owned by Rust's `mw_check_model_compatibility`; Python only forwards the structurally checked tensor descriptors and returns the native explanation. Copied Diffusers parts pass this same policy again before their inference test. Header byte/offset validation and Diffusers folder configuration checks remain in Python. This move does not change inference settings, supported architectures, adapter versions or existing ready-state stamps.

Discover supports public root-level single-file SD 1.5-family safetensors checkpoints. Search requests public file/card metadata and presents file-availability hints and the reported license; these hints are not a compatibility decision. **Check model** obtains a repository commit with `blobs=true` file metadata, then calls Rust's additive ABI 1 `mw_plan_hub_model`. This pure, bounded policy requires public access, a stated license, an immutable 40-digit commit, safe root-level filenames, declared sizes (at most 32 GiB), and published LFS SHA-256 values. It excludes individual Diffusers components and sharded parts, caps files/candidates, and sorts by size/name. No network, disk work, or readiness transition occurs inside the planner.

The worker selects the smallest candidate by default and reads only its prefix/header over HTTPS at that commit (at most 8 MiB). Range responses must describe the requested bytes and declared total; servers that ignore Range are read only as far as the bounded header. The same `model_library.parse_header` and checkpoint identification used for local imports check architecture, shapes and number formats. No model code or remote configuration is loaded. Hardware choice, quota-aware drive space, and the ready bundled runtime are checked independently. A refusal leaves no installation folder. Another candidate can be selected under **Advanced options** and checked at the same revision.

**Download and test** requires the model-card/license review. Its request carries the checked commit, filename, exact byte count and SHA-256; the worker re-resolves that immutable snapshot and rejects mismatches, so a publisher changing `main` cannot silently replace the reviewed model. Under the ordinary data-folder lock it checks baseline readiness/free space again, rejects duplicates before the large transfer, and streams directly into a new import folder's `model.safetensors.partial`. There is one full copy and no persistent Hub download cache. Size/hash checks, periodic free-space checks and bounded, throttled byte progress run during the transfer; available socket bytes are processed without waiting to fill a large read. Only HTTPS redirects within Hugging Face's download domains are accepted. The file is flushed/synced and renamed only after matching its published digest.

Pinned root model cards, licenses and notices are retained under `notices/` (each at most 1 MiB, verified against its published Git blob ID). They are included in native verification and readiness stamps, but never loaded as model configuration. Finalization reuses the local-import duplicate/configuration/native-verification/real-GPU-test path; only its passing result becomes ready. Failure/cancellation removes the first addition; a killed worker leaves an existing `copying`/`testing` record that normal idle import recovery removes. Cancelled downloads restart rather than resume. No images or generation records are deleted. A downloaded model's `source` records provider, repository, commit, file, SHA-256 and license metadata, and generation preserves that source instead of replacing it with a local-file label.

Existing alpha.13 installations and local imports retain their stamps because inference loading and adapter semantics are unchanged. Direct Diffusers-folder downloads, protected Hub access, other architectures, add-ons and video remain unsupported here. Local Diffusers-folder import remains available. MCP has no arbitrary-model download tool; its setup capability is still confined to the bundled recipe.

The public API metadata follows the official [Hub API](https://huggingface.co/docs/hub/api) and [file metadata reference](https://huggingface.co/docs/huggingface_hub/package_reference/hf_api#huggingface_hub.HfApi.model_info). The opt-in `tests/online_catalog_check.py` validates real metadata and a bounded pinned header without full weights; `tests/gpu_model_import_check.py <data-folder> hf:publisher/model --license-reviewed` exercises the complete download/GPU/use/removal path and keeps its generated images/jobs. Routine tests use sparse fake weights and no network or GPU.

## Models you added

Create → **Add a model you already downloaded** accepts an SD 1.5-family model the user already has: one `.safetensors` checkpoint in the original single-file layout, or a Diffusers folder (`model_index.json` plus `unet/`, `text_encoder/`, and optionally `vae/` safetensors weights, `.fp16` variants included). It requires a ready bundled installation, because added models reuse its private `sd15-cu126-v1` runtime and its tokenizer, scheduler, safety checker, and configuration files; nothing new downloads.

**Identification without running model code.** `model_library.py` (standard library only, in the discovery interpreter) reads each safetensors header: an 8-byte length, then JSON naming every tensor's type, shape, and byte range. It requires that the ranges describe the whole file (a short file is reported as still downloading) and checks SD 1.5's layout: a 4-channel UNet input convolution of 320 filters with matching output, 768-wide cross-attention, a 49408 × 768 CLIP text embedding, and the standard VAE shapes when a VAE is present. Weights must be 16- or 32-bit floats. Recognized non-matches are refused with what they are — SDXL, SD 2, SD 3, FLUX, dedicated inpainting or InstructPix2Pix UNets, LoRAs, textual-inversion embeddings, ControlNets, a lone UNet/VAE/text encoder, quantized formats, split weights — and anything else is "not a model Media Workbench recognizes". Pickle-based `.ckpt`, `.pt`, `.pth`, and `.bin` files are refused before they are opened, since loading them can execute code. A folder's own configuration files and `model_index.json` class names are never used to load anything.

**Copy, do not reference.** The model is copied to `models/imported/<id>/` (single files as `model.safetensors`; Diffusers parts under their usual names without variant suffixes), and the user's original is never modified. Rust's `mw_import_file` streams each file once, hashing as it copies, opens the source with read-only sharing on Windows so it cannot be written meanwhile, refuses a source that changed during the copy, syncs, and renames the finished copy into place; cancellation or failure removes the partial file. Copying costs disk space (the app says so and checks free space first), but the verified bytes are then in the application's own link-free folder: moving, editing, or deleting the original cannot silently change or break a ready model, the existing native verifier and size/mtime stamps apply unchanged, and removing an added model never touches the user's files. Afterwards the user may delete their original.

**Readiness.** The record `models/imported/<id>/model.json` stores the name, format, source file name, each copied file's size and SHA-256, and whether the model brings its own VAE. Diffusers parts receive the bundled SD 1.5 `config.json` files. The import then re-verifies every copy through `mw_verify_file`, identifies the copy again from its own headers, rejects a duplicate of an already added model, and runs the same 512 × 512, four-step GPU test as the bundled model (`verify-model`), with the same output checks and safety checker. The test uses the bundled installation's verified runtime first and falls back to `fp32-offload` if the model fails with it. Only then does the record become ready, with the GPU evidence, the runtime it passed with, `IMPORT_ADAPTER_VERSION` (2 since the runtime choice was added), the profile stamp for that runtime, and size/mtime stamps of every file in its folder; generation runs the model with that runtime. If any step fails or is cancelled, the folder is removed and nothing is listed; an import interrupted by a crash is removed by the next idle recovery. An added model is ready only while its stamps match, its adapter version and its runtime's profile stamp are current, and the bundled installation itself is ready; otherwise it needs a new test. **Test again** in Settings re-verifies the copies and re-runs the GPU test, recording a failure if they no longer pass.

**Loading.** The ML child builds an added model only from safetensors in its copy, with every configuration from the bundled SD 1.5 folder and `local_files_only`: single files through Diffusers' `from_single_file` with the bundled folder as `config`, Diffusers parts through their model classes; tokenizer, PNDM scheduler, feature extractor, and safety checker always come from the bundled model, as does the VAE when the added model has none. Image-to-image and painted changes reuse those components through `from_pipe`. Added models load in the precision of their verified runtime.

**Use.** Create shows a **Model** chooser only when an added model is ready. Generation names the model (`model` is `sd15-baseline` or an added ID); the coordinator checks that model's readiness before writing a job, and the job record stores `settings.model`, `model`, `modelName`, and a local source description (file name and SHA-256). Library describes images made with an added model by name, and **Use settings** selects that model again, or falls back to the bundled model with a note when it was removed or needs a new test. Upscaling is independent of the chosen model. Settings → Storage measures `models/imported` separately, lists each added model with its size and state, and removes one after confirmation under the data-folder lock; images, job records, and the bundled model are kept, and removing the bundled installation keeps added models, which wait until it is set up again.

## Data and recovery

```text
<data folder>/
  .operation.lock                     OS-released exclusive lock
  bootstrap/                          verified Python/uv archives and uv executable
  runtimes/sd15-cu126-v1/python/       private interpreter and packages
  models/sd15-baseline/               selected model files and Hub download metadata
  models/imported/<id>/               a model the user added: copied weights and model.json
  cache/uv/                           wheel cache, separate from system caches
  jobs/install-sd15.json              latest setup attempt and readiness evidence
  jobs/<id>.json                     generation settings, status, output evidence and timings
  artifacts/<id>/image.png            finalized generated image
  library/index.sqlite3              rebuildable metadata index (no images)
  logs/<operation>-<id>.log           local child output/diagnostics (generation logs use the job ID)
  .removing/                          caches being removed; finished by the next clean-up after a crash
```

One operation owns a data folder at a time, including across separate clients. Setup writes preparing/runtime/downloading/verifying states before each stage; ready is atomic and last. Normal failures and cancellation record their outcome. Work left in progress with no lock owner is changed to interrupted the next time the folder is idle and checked: a setup attempt at status, install, or generation; a `running` generation job at status, Library, install, or generation. Recovery removes that job's `image.partial`, unfinished atomic-write temporary records, and reports how many jobs it recorded so Library can say so. Damaged job records are skipped rather than blocking Library. A changed readiness stamp, or a model file whose size or modification time changed, invalidates readiness. Retry retains completed downloads (unfinished ones for three days); no rollback deletes a previous model/runtime automatically. Besides the automatic clean-up below, removal happens when the user asks in Settings → Storage (`storage.clear`): download caches (`cache/`, `bootstrap/`), logs, or the installation (the ready record first, then runtime, model, and caches). It takes the data-folder lock, so it waits for no one and fails if another operation owns the folder; images and job records are never removed.

Cancellation reaches the child through the coordinator and kills the ML process if needed. The C# transport escalates after three seconds to terminating its owned process tree. GPU kernels/imports are not guaranteed to exit cooperatively. Each worker is placed in its own Windows Job Object with kill-on-close before it receives a request, so the ML child, uv, and any other descendant inherit it. Forced stops terminate the whole job, including a descendant whose coordinator already exited; disposing a worker closes its job; and if the app itself crashes or is killed, Windows closes the handle and ends the tree. The coordinator's lock is then released and the next check records the job as interrupted. Partial, uncommitted outputs do not enter Library. Library pages through all matching successful images (48 per page in the GUI; worker limits 1–200) and shows up to 50 recent failed, cancelled, or interrupted jobs independently of image filters. Search matches literal Unicode-casefolded substrings of prompts, negative prompts, seeds, and job IDs; kind filters select generated or upscaled images. The page order is job-file modification time, newest first, with filename as a deterministic tie-breaker. Offsets can shift when records change; Search / refresh restarts at the newest page. Each generation writes its child log to `logs/generate-<id>.log`, and Library links it only by that fixed name. A derived SQLite index under `library/` stores job metadata and query indexes; JSON records remain authoritative. Each refresh scans job-file sizes/mtimes, decodes changed records, removes deleted records from the index, and rechecks image containment/existence. It still performs linear filesystem work; the index avoids decoding every record and returning the whole library. Missing, corrupt, or incompatible indexes rebuild automatically under their own lock, without changing records or requiring the inference lock. Active jobs are recovered only if the inference lock is available. Cancelled refreshes roll back their SQLite transaction. Use settings restores original controls for successful images and unfinished jobs, routing upscales to Tools and other images to Create; private input copies resolve from the current data folder. It resolves each image path inside that job's `artifacts/<id>/` folder before listing it; records from 0.2.0-alpha.1 that stored an absolute path are re-rooted by job ID, so they remain listed after the data folder moves.

## Clean-up and free space

Automatic clean-up is one Rust service, `mw_tidy_data_folder` (see [native ABI](native-abi.md#automatic-clean-up)), so every client applies the same rules. It takes the data-folder lock itself and does nothing while setup, generation, a model import, or a removal owns the folder. The desktop runs it once at startup (after reading installation status, so download caches are removed only from a verified installation, and only when Settings → **Keep setup's download files for repairs** is off); the worker runs it after a verified Install / verify, before reporting how much it freed as `cleanedBytes`. A failed or busy clean-up never fails setup; the next start tries again. It keeps the newest 50 failed, cancelled, and interrupted job records (exactly the ones Library lists) with their private inputs and logs, removing older ones with their input copies and logs but never a finished `image.png`; keeps logs to the newest 300 and the last 30 days, never removing the log of a running or listed unfinished job; removes `.partial`/`.incomplete` setup downloads older than 72 hours, or all of them once setup is verified; and removes `cache/` and `bootstrap/` by renaming them into `.removing/` first. Images, succeeded and damaged records, the pictures **Use settings** needs, models the user added, and anything it does not recognize are kept. It also removes `temp/work/<32 hex>` folders whose worker is gone: a running worker holds `.owner` open, which Windows refuses to delete, and a folder without one is left for ten minutes in case its worker is just starting. The desktop also deletes, at startup, painted-area hand-over files older than an hour in the data folder's `temp/painted` (normally deleted right after the worker copies them), update installers in `temp/updates` for the running version or older, interrupted installer downloads, and newer installers unused for a week; it sweeps the same names from the `%TEMP%` locations earlier versions used. `%LOCALAPPDATA%\MediaWorkbench\Logs\startup.log` rolls over to `startup.old.log` past 1 MiB.

Generation and upscaling check free space under the lock, before writing the job record, input copies, or log: room for the private input copies, the largest picture the job can save as an uncompressed RGB PNG (768 pixels a side for ordinary generation, 4096 for painted changes, 4096 or 8192 for 2× or 4× upscales), and 256 MiB for logs and Windows. Too little space refuses the job with the free and needed sizes and how to fix it; nothing is written. Setup (20 GiB, or missing files plus 2 GiB) and adding a model already checked space. `mw_drive_info` reports free space and drive kind without creating the folder; Create, Tools, and Settings warn below 5 GiB free, and Create (once set up) and Settings note when the data folder is on a hard disk, USB, or network drive and suggest an SSD for faster model loading.

### Load time versus inference time

Since 0.2.0-alpha.16 the ML child times three phases separately and every successful generation, upscale and GPU verification records them: `startupSeconds` (importing PyTorch/Diffusers and the CUDA checks), `loadSeconds` (reading the model and placing it on the GPU or preparing offloading; for upscales, loading Real-ESRGAN), and `seconds` (the inference itself, as before). With memory-saving (offloaded) settings, moving each part to the GPU happens during inference, so part of the transfer is counted in `seconds`. After a generation, the coordinator compares `loadSeconds` with the weight bytes the job read (the bundled 2.55 GiB of SD 1.5 safetensors, or an added model's copied files plus the bundled parts it borrows) and the data folder's drive kind from `mw_drive_info`, through `hardware.load_note`. Loads under 20 seconds say nothing. A slower load on a hard disk, USB or network drive names that drive and suggests moving the data folder; on a solid-state drive (or one of unknown type) it says so only when the effective rate is below 100 MiB/s, describing the drive or the computer as busy at the time. The plain sentence is stored as `loadNote` in the job record and Create shows it after the picture is saved; an unreadable drive never fails a finished job. Windows' file cache makes a repeated load much faster than the first, so the note mostly appears for the first picture after starting the computer or changing models. The thresholds are not yet calibrated against a real hard-disk data folder.

## Image export

Library and the latest Create/Tools result offer Open image (the default PNG viewer) and Save a copy. The native Windows App SDK save picker returns a path without creating a placeholder; the worker validates that the resolved destination is outside the managed data folder. Rust owns this operation via `mw_export_artifact`: it accepts only a completed job ID, resolves its original inside its own artifact folder, streams a temporary file on the destination volume, and verifies the recorded image SHA-256 before atomic replacement. The desktop calls Rust directly on a background thread; `library.export` is the worker adapter for other clients. Failure or cooperative cancellation removes the temporary file and preserves any existing destination. Copies are byte-identical PNGs; the original's prompts, settings, and job JSON remain in Library. The operation needs neither a GPU nor the inference runtime.

## Stable Diffusion XL

Create's **Get Stable Diffusion XL for larger, more detailed pictures** (shown once Stable Diffusion 1.5 is ready) sets up SDXL base 1.0 as an optional verified model. `workers/python/sdxl.py` and the shared `addon.py` check free space and the hardware, have the ML child download the pinned files (`profiles/sdxl-files.json`: fp16 safetensors for both text encoders, the UNet and the VAE, with configurations, tokenizers, the model card and the CreativeML Open RAIL++-M license, 6.9 GB at an immutable commit) through the Hub cache, verify every file through Rust's `mw_verify_file`, and run a real 4-step 1024 × 1024 picture on the GPU. Only then is `jobs/install-sdxl.json` written as ready, with its own stamp (SDXL adapter version 1, runtime choice, the pinned manifest, the shared runtime lock) and size/modification-time stamps. It also needs a ready Stable Diffusion 1.5 installation, whose runtime and safety checker it uses. `models.list` lists it after Stable Diffusion 1.5 (`sdxl-base`, `builtIn`, format `bundled-xl`), and Create's **Model** choice offers it once ready.

Its runtime choices follow the same rules as pictures, sized for its UNet (about three times SD 1.5's): `xl-fp16-model` (half precision, model offloading, 8 GB), `xl-fp16-sequential` (half precision, streaming, 6 GB), `xl-fp32-model` (full precision, model offloading, 16 GB), and the conservative `xl-fp32-sequential` (full precision, streaming, 6 GB). Full precision keeps about 13 GB of weights in system memory, so it is refused with a plain reason below 16 GB of memory; a failed faster choice falls back to the conservative one and is remembered for that card and driver. Pictures use SDXL's trained sizes (1024 × 1024, 832 × 1216, 1216 × 832; starting pictures take the nearest of them), its own Euler scheduler unless another sampler is chosen, VAE slicing and tiling, and no watermark. Image-to-image and painted changes use the SDXL image-to-image and inpainting pipelines on the same weights, with painted regions at least 768 pixels across. SDXL has no safety checker of its own, so Stable Diffusion 1.5's checker reviews each picture on the CPU. Job records name the model (`model` `sdxl-base`, `modelName`) and the pinned SDXL source; **Use settings** chooses it again before its shape. Settings can remove it (its pictures are kept), and removing Stable Diffusion 1.5 removes it too. Only the conservative choice can be observed on the development GPU; the others are verified per machine by the same test.
## Short videos

Create's **What to make → A short video** makes 2- or 3-second clips (16 or 24 frames at 8 frames a second) at the three SD 1.5 sizes with the bundled Stable Diffusion 1.5 and AnimateDiff's motion adapter v1-5-3. Videos have their own setup after Stable Diffusion 1.5 is verified: **Set up videos** (`video.install`, `workers/python/video.py`) checks free space and the hardware, downloads the pinned adapter (`profiles/video-files.json`: config, model card and 1.67 GB safetensors at an immutable commit) with the stdlib downloader, verifies every file through Rust's `mw_verify_file`, and runs the real test: a 16-frame, 4-step 512 × 512 clip made on the GPU by the ML child and encoded to MP4 by Rust's `mw_encode_video`. Only then is `jobs/install-video.json` written as ready, with its own stamp (video adapter version 1, runtime choice, the pinned manifest, and the shared runtime lock) and size/modification-time stamps of the adapter files. Readiness also requires a ready Stable Diffusion 1.5 installation; changed files, a changed stamp, or a base that needs Install / verify each say plainly what to do.

The runtime choice for videos is separate from pictures, because AnimateDiff runs the UNet with its motion layers (about 1.5 times its size) across every frame at once: `video-fp16-model` (half precision, model offloading, 8 GB or more and a card trusted with half precision), `video-fp16-sequential` (half precision, layer-by-layer streaming, 6 GB), `video-fp32-model` (full precision, model offloading, 12 GB), and the conservative `video-fp32-sequential` (full precision, streaming, 6 GB), which every supported card can use. Create and the setup card say plainly that streaming fits 6 GB but can take several minutes per video. A failed faster choice falls back to `video-fp32-sequential` and is remembered for that card and driver, as for pictures. Only that conservative choice has been observed on real hardware so far (see [validation](validation.md)); the others are verified per machine by the same test before they are used.

The ML child loads the bundled SD 1.5 weights (offline, safetensors only) and the adapter, builds `AnimateDiffPipeline.from_pipe` with the DDIM scheduler settings AnimateDiff was trained with (linear betas, no sample clipping, linspace timesteps, offset 1), and checks every frame with the model's safety checker on the CPU, since AnimateDiff has none of its own. It writes raw RGB frames (`frames.rgb`) and the first frame as `poster.png`; the coordinator encodes `video.mp4` through Rust and deletes the frames. The job record (`kind` `video`) keeps the settings (`frames`, `fps`, sampler `ddim`), the poster as `imagePath`/`imageSha256`, `videoPath`/`videoSha256`, the runtime, and the startup/load/inference timings, and its log is `logs/video-<id>.log`. Library shows the poster, filters by **Videos**, plays the MP4 in the default player, and **Save a copy** exports a verified MP4. Create plays the latest video on a loop. Space is checked first for the raw frames, the largest MP4 and the poster. Failed or cancelled videos, interrupted ones found by recovery, and Rust's clean-up remove raw frames, partial MP4s and orphaned posters; finished videos and their posters are kept. Removing the video setup (Settings) removes the adapter and its record and keeps every video; removing Stable Diffusion 1.5 removes the adapter too.

Not yet: videos from models the user added, starting a video from a picture, longer clips, other video models, and audio. Windows editions without Media Foundation (N editions without the Media Feature Pack) cannot finish video setup and are told how to add it.

### Image-to-image with memory-saving settings

Model offloading moves a pipeline part off the GPU only when the next part in its order (text encoder, UNet, VAE) runs. A starting picture (and a painted change's masked picture) is encoded by the VAE before denoising, so before 0.3.0-alpha.6 the VAE stayed on the GPU beside the UNet for every step; on a 6 GB card Windows then spilled graphics memory into shared system memory and each step took about six times as long. `vae_off_while_denoising` registers a pre-hook on the UNet that moves the VAE back to the CPU; offloading moves it in again to decode. The numbers are unchanged (byte-identical pictures in the real A/B check), so readiness is unaffected.

### Keeping the picture model loaded

Since 0.3.0-alpha.5 the desktop (and the local MCP host) run picture, upscale and video jobs in one long-running coordinator started with `MEDIA_WORKBENCH_KEEP_MODEL=1` (`WorkbenchService`). For **pictures** that coordinator keeps one ML child alive between jobs (`inference_setup.KeptModel`, `inference_worker.py --operation serve`). The child keeps the PyTorch runtime and the last pipeline, and reuses it only when the next picture uses exactly the same model, runtime choice and mode (text, starting picture, or painted change). Anything else releases it and loads fresh, so two models are never in graphics memory at once. Every picture starts from a new instance of the model's own scheduler, its own seeded generator and reset peak-memory statistics; reused pictures record `keptLoaded`, zero `startupSeconds`/`loadSeconds`, and Create says the model was still loaded.

While the child lives, its coordinator holds the data-folder lock (`_acquire(root, kept=True)`), so another program (another window, an MCP client in another process) cannot load a second model onto the same card; it gets a plain "busy" message naming the kept model and its idle release. Jobs of the same coordinator nest with that hold. The kept child is discarded after any error, cancellation or exit, and released before every other job in the coordinator (setup tests, downloads, upscaling and videos run alone on the card). The desktop releases it before any operation that needs the data folder to itself (setup, model import/retest/removal, storage clearing, clean-up, moving), when another data folder is used, after **two idle minutes**, and when the app exits (the Windows Job Object still owns the whole tree). Reads (status, Library, model list, storage, hardware profile, Hub) leave it loaded. The graphics memory a picture used stays reserved until the release; emptying PyTorch's cache after each picture made reuse about 4 s slower on the development GPU, so it is not done.

Verification, the adapter version and readiness stamps are unchanged: setup tests still run in a fresh one-shot child, and the opt-in `tests/gpu_kept_model_check.py` shows that kept pictures are byte-identical to a fresh child's for the same settings. On a GTX 1660 Ti with `fp32-offload`, 12-step 512 × 512 pictures took about 24–26 s with a fresh child and 15.6–15.9 s when kept (see [validation](validation.md)).

## Current limits
Windows x64/NVIDIA only; the bundled SD 1.5 model, the optional Stable Diffusion XL base, and SD 1.5-family models the user adds (no other added architectures, LoRAs, or embeddings yet); three sizes (verification itself runs only 512 × 512, so the larger sizes are not tested per machine); four runtime choices, of which only `fp32-offload` has passed on real hardware so far (a GTX 1660 Ti; see [validation](validation.md)). No account tokens, LoRAs, dedicated inpainting checkpoint, video beyond the short SD 1.5 clips above, queue, Library image pruning, signature-verified updates, or telemetry. Only pictures reuse a loaded model (for two idle minutes); upscales and videos still load theirs each time, and there is no queue. Setup needs substantially more disk than the model alone while it runs; its download caches are removed once it passes its test unless kept. Installed package hashes are enforced on download, rather than continuously auditing every extracted package file. The worker is dependency/process isolation, not a hostile-code sandbox. Clean-machine Visual C++ runtime and Windows 10 testing remain necessary before broad support claims.
