**Removing the old copy (0.3.0-alpha.4):** after a move, Settings offers **Remove the old copy…** (with a confirmation flyout; remembered across restarts as `MovedFrom`). Rust `mw_remove_moved_data` holds the old folder's lock and deletes only files whose copy in the current data folder has the same size and modification time, plus the old folder's own `temp/`, `library/` and `.removing/`, then empty folders, the lock file and the folder itself if empty. Files that differ or were added later are kept and counted. Saving a different folder forgets the old copy.

**Never-use drives (0.3.0-alpha.4):** each drive in Settings has **Never use this drive** / **Allow this drive** (saved as `ExcludedDrives`, by drive root; a mounted folder counts as the drive whose letter it is under). The choice is remembered (`DataRootChosen` in preferences); folders saved by earlier versions count as chosen, and a ready installation is never asked. Installer: Inno Setup already reuses the previous install folder on upgrade (`UsePreviousAppDir` default) and shows the destination page only on first install (`DisableDirPage=auto`); its own unpacking uses Windows temp briefly. No installer change was made in this slice.

**Slice 3 implemented (0.3.0-alpha.3):** Settings → **Move my data there…** checks the typed folder with Rust `mw_plan_data_move` (files and bytes to copy, free space with a 1 GiB reserve, same-volume note, and plain blockers: inside/containing the data folder, not empty, a link inside the data folder, not enough space), then **Move now** runs `mw_move_data_folder`: under the data-folder lock it copies everything except `.operation.lock`, `temp/`, `library/` (rebuilt) and `.removing/` into a marked `.<name>.moving` staging folder, hashes each file while reading, re-reads and compares the copy, keeps modification times (readiness stamps compare size and time), re-checks free space before every file, and renames the staging folder into place last. Only then are settings switched. The old folder is never changed; the app says it can be deleted in File Explorer once the new one is checked. Failure or cancellation removes the staging folder; a crash is recovered at the next start from `PendingMove` in preferences. Readiness carries over because the bytes and times are identical and the runtime, job and readiness records hold no absolute paths (checked on the development data folder); no GPU run after a real move has been made yet.

**Kept-loaded picture model (0.3.0-alpha.5):** picture/upscale/video jobs share one long-running coordinator; pictures reuse a loaded model for two idle minutes while the coordinator holds the data-folder lock; anything needing the folder releases it first. Real GPU check `tests/gpu_kept_model_check.py` passed (byte-identical pictures, 15.6 s vs 25 s). See [inference](docs/inference.md#keeping-the-picture-model-loaded).

**Waiting pictures (0.3.0-alpha.8).** Create's **Add to queue** saves the picture it describes (each version with **How many**) without making it: `picture_queue.py` validates it like a generation, copies any starting picture and painted area into `queue/<id>/`, and writes `queue/<id>.json` (status `queued`, settings with relative input names) atomically before answering. The queue has its own folder so Library, clean-up and recovery never see waiting pictures; a damaged record is skipped, never deleted, and a folder whose record was never written is removed after ten minutes. **Run queue** makes them oldest first through the ordinary generation path (the job makes its own private copies, and the kept model makes repeats faster), removing each item after its attempt; a failed one becomes an ordinary failed job with Retry in Library and the rest still run. **Cancel** stops the current picture and leaves it and the rest waiting. Waiting pictures are listed after a restart and run only when the user selects Run queue. Queue operations do not need the data folder to themselves, so they leave a kept model loaded. Up to 200 pictures can wait. Since 0.3.0-alpha.9, **Add to queue** also works while a picture or the queue is being made (not during setup, moves or removals), and a running queue reads the queue again before each picture, so pictures added meanwhile are made too. Not yet: videos and upscales in the queue, and MCP access.

**Added SDXL models (0.3.0-alpha.7):** single-file SDXL base-family checkpoints (fine-tunes) can be added locally or downloaded from Discover. Rust `mw_check_model_compatibility` now returns `family` (`sd15`/`sdxl`) and refuses SDXL refiners, SDXL inpainting models and SDXL Diffusers parts with plain reasons. Added SDXL models need the verified Stable Diffusion XL setup (they borrow its configuration, VAE when missing, and verified runtime choice), are tested with SDXL's 1024 × 1024 test (`verify-xl` with `family`), store SDXL's profile stamp, and generate only at SDXL sizes. Real GPU check passed through Discover (see validation).

**Several versions per Generate (0.3.0-alpha.7):** Create's **How many** (1 picture, 2 or 4 versions) runs consecutive seeds in one operation; after the first each reuses the kept model. A version refused by the worker (for example the safety checker) is reported and the rest still run; if all fail it is an ordinary failure. Seeds wrap after 4294967295. Cancel stops the remaining versions. Headless view-model checks only (`BatchChecks.cs`).

**Image-to-image speed (0.3.0-alpha.6):** with model offloading, the VAE that encodes a starting picture stayed on the GPU beside the UNet; on 6 GB cards that spilled into shared memory (5.6 s per step instead of 0.93 s). `inference_worker.vae_off_while_denoising` moves it off before each UNet call. Real GPU A/B on the GTX 1660 Ti: image-to-image 47.9 -> 11.3 s, painted change 77.0 -> 16.3 s inference, byte-identical outputs, peak 5166 -> 4841 MiB. No adapter-version change: outputs are identical and setup tests (text pictures) never used it.

**Installer reopen fix (0.3.0-alpha.5):** the installer reopens the app after a silent installation only when it is not `/VERYSILENT` (`ReopenAfterUpdate` in `packaging/media-workbench.iss`). Every app version's in-app updater passes `/SILENT`, so updates still reopen the app; unattended installations no longer open a window. ## Build, check, run

The user relies on this computer during development. Prefer headless work; announce necessary desktop control and explain any apparently idle window before using it. A user interruption stops automation and is not failure evidence. Keep each milestone tested, documented, committed and released through Actions; keep this handoff current when switching assistants or approaching the end of a session. Session-usage counters are not available to the development agent.

From the repository root in PowerShell:

```powershell
./scripts/build.ps1
./scripts/check.ps1
./scripts/build.ps1 -Configuration Release -Publish
./scripts/test-publish.ps1 -SkipUI
./scripts/run.ps1 -NoBuild
```

Build prerequisites: Windows x64, the SDK selected by `global.json` (10.0.113, patch-only roll-forward), Rustup with `rust-toolchain.toml` (1.97.0, rustfmt and Clippy), and Visual Studio 2022 Build Tools with the MSVC x64 toolchain and Windows SDK. The project targets Windows SDK 26100; the NuGet BuildTools version is pinned separately. Cargo runs from the repository root so `.cargo/config.toml` selects static MSVC CRT linkage. The x64 build maps to `x86_64-pc-windows-msvc`; other architectures are rejected. Design-time builds do not invoke Cargo.

`build.ps1` prepares checksum-verified private tooling, builds Rust and the solution, and copies a console host beside the GUI for development MCP use. It may download missing dependencies. `check.ps1` runs Rust formatting/tests/Clippy, Python tests, and C# boundary/MCP/presentation checks; it does not provision ML models. `-Artifacts <absolute-folder>` redirects disposable C# check data when the project drive is busy. `-Online` adds public Hub discovery validation.

`-Publish` produces a self-contained Release folder and runs headless published checks. `test-publish.ps1` adds actual window/XAML initialization on an interactive desktop. The published folder is `artifacts/publish/win-x64`; normal Debug GUI output is `artifacts/dotnet/bin/MediaWorkbench.App/debug_win-x64`. Installer production and release publication belong to GitHub Actions. Push a changed `<Version>` and matching dated changelog section together; never manually create the release from this computer.

Routine restore updates locks only when inputs change. To deliberately change a dependency, update `Directory.Packages.props`, run `dotnet restore MediaWorkbench.slnx --force-evaluate --artifacts-path artifacts/dotnet`, review all `packages.lock.json` changes, then run checks/publish. CI sets `ContinuousIntegrationBuild=true`, which enables NuGet locked mode for every restore, including implicit build/publish restores. `dotnet restore MediaWorkbench.slnx --locked-mode --artifacts-path artifacts/dotnet` reproduces the graph check locally.

## Ownership, locations, and shutdown

- ABI/header: `native/include/media_workbench.h`; contract: [native ABI](docs/native-abi.md). Rust owns planning, tensor-layout compatibility, path policy, verified export, storage inventory, pinned-file verification, import copying, drive information and automatic data-folder clean-up.
- C# Core/Presentation/Infrastructure own typed projections, UI state, OS services, native bindings, and worker/process lifetime. WinUI code handles views, navigation, pickers, activation, and painting input. Native buffers are copied and callbacks are retained only until a call returns.
- Standard-library Python coordinates Hub/setup, job records, model readiness and the Library index. ML packages run only in a separate isolated Python child. Windows Job Objects terminate the entire owned tree on cancellation/crash. New queue/warm-worker work must preserve this protocol.
- The saved absolute data folder is selected in Settings. Its models, runtimes, artifacts, private input copies, jobs, caches, index and logs are outside the app installation. Settings changes do not migrate data. `%LOCALAPPDATA%/MediaWorkbench/settings.json` holds local preferences; the data folder's `temp/` holds worker scratch, painted hand-overs and update staging (`WorkFolders.cs`).
- `runtime/`, `artifacts/`, `.cache/`, `.tools/`, `.local/` and `dist/` are ignored. Never commit models, machine settings, binaries, generated images, private paths or credentials. Preserve MIT and third-party/model notices.
